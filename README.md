# Dependency Graph Visualizer — Вариант 4

## Общее описание
Консольный инструмент на Python для визуализации графа зависимостей пакетов
Rust (Cargo). Использует только стандартную библиотеку Python.

Программа запрашивает у реестра пакетов (crates.io) список зависимостей
заданного пакета (или читает граф из тестового файла), строит граф обходом
в ширину с учётом максимальной глубины, фильтра по подстроке и циклических
зависимостей, а затем выводит результат списком, ASCII-деревом и изображением
(через PlantUML). Есть режим обратных зависимостей (какие пакеты зависят
от заданного).

## Функции и настройки

### Конфигурационный файл (JSON)
Путь к нему задаётся параметром `--config`. Все параметры обязательны и
проверяются, при ошибке выводится понятное сообщение.

| Параметр | Описание |
|----------|----------|
| `package_name` | имя анализируемого пакета |
| `repository` | URL реестра пакетов (`https://index.crates.io`); в тестовом режиме — путь к файлу тестового репозитория |
| `test_mode` | `true` — тестовый режим, `false` — настоящий реестр |
| `ascii_tree` | `true` — дополнительно вывести граф в виде ASCII-дерева |
| `max_depth` | максимальная глубина анализа, целое число не меньше 1 (1 — только прямые зависимости) |
| `filter_substring` | пакеты, в имени которых есть эта подстрока, пропускаются (пустая строка — без фильтра) |

### Параметры командной строки
| Параметр | Описание |
|----------|----------|
| `--config` | путь к JSON-файлу конфигурации (по умолчанию `config.json`) |
| `--show-config` | вывести параметры конфигурации в формате ключ-значение |
| `--reverse` | вывести обратные зависимости (только в тестовом режиме) |
| `--image` | построить и показать изображение графа |
| `--jar` | путь к `plantuml.jar` (по умолчанию `tools/plantuml.jar`) |
| `--out` | куда сохранить описание PlantUML (по умолчанию `output/graph.puml`) |

### Как получаются зависимости
Реестр хранит о каждом пакете один текстовый файл: в каждой строке — описание
одной версии пакета в формате JSON, включая список её зависимостей. Программа
выбирает последнюю версию, не отозванную автором, и берёт из неё обычные
зависимости. Необязательные зависимости, зависимости только для разработки
и сборки, а также привязанные к определённой платформе пропускаются.
При сбое сети запрос повторяется до трёх раз.

### Тестовый репозиторий
Файл, где каждая строка описывает один пакет: `A: B C` означает, что пакет `A`
зависит от `B` и `C`. Имена пакетов — большие латинские буквы. Строки,
начинающиеся с `#`, — комментарии. Примеры лежат в `tests/data/`.

### Как работает построение графа
- Обход в ширину: сначала прямые зависимости, потом зависимости зависимостей
  и так до `max_depth`. Реализован рекурсивно: пакеты берутся из очереди по
  одному, их зависимости добавляются в конец очереди.
- Циклы не приводят к зависанию: уже встреченный пакет повторно не добавляется
  в очередь.
- Пакеты, которых нет в реестре, считаются конечными узлами графа.
- Фильтр исключает пакеты с заданной подстрокой вместе с их ветками.

## Сборка и тесты
Сборка не требуется. Нужен Python 3.

Для изображений дополнительно нужны Java и файл `plantuml.jar` в папке `tools/`.
Для Java 8 подходит версия 1.2022.8:
https://repo1.maven.org/maven2/net/sourceforge/plantuml/plantuml/1.2022.8/plantuml-1.2022.8.jar
(файл нужно сохранить как `tools/plantuml.jar`; в репозиторий он не входит).

Запуск автотестов:
```
python -m unittest discover tests
```

Запуск программы:
```
run.bat --config config.test.json
```
или напрямую:
```
python src/main.py --config config.test.json
```

Демонстрационные сценарии (по этапам):
```
python tests/demo_errors.py     # этап 1: обработка ошибок для всех параметров
python tests/demo_graph.py      # этап 3: глубина, фильтр, циклы
python tests/demo_reverse.py    # этап 4: обратные зависимости
python tests/demo_visual.py     # этап 5: визуализация трёх пакетов
```

## Примеры использования

Настоящий реестр (`config.example.json`):
```
$ python src/main.py --config config.example.json
Граф зависимостей пакета serde:
  serde -> serde_core
  serde_core -> (нет зависимостей)

ASCII-дерево:
  serde
  `-- serde_core
```

Тестовый режим (`config.test.json`):
```
$ python src/main.py --config config.test.json
Граф зависимостей пакета A:
  A -> B, C
  B -> D
  C -> D, E
  D -> (нет зависимостей)
  E -> F

ASCII-дерево:
  A
  |-- B
  |   `-- D
  `-- C
      |-- D (уже показан)
      `-- E
          `-- F
```

Обратные зависимости (`config.reverse.json`):
```
$ python src/main.py --config config.reverse.json --reverse
Обратные зависимости пакета D (кто от него зависит):
  D <- B, C
  B <- A
  C <- A
  A <- (от него никто не зависит)
```

Изображение графа (`--image`) строится из такого описания PlantUML:
```
@startuml
skinparam shadowing false
left to right direction
rectangle "A" as n0 #LightBlue
rectangle "B" as n1
rectangle "C" as n2
rectangle "D" as n3
rectangle "E" as n4
rectangle "F" as n5
n0 --> n1
n0 --> n2
n1 --> n3
n2 --> n3
n2 --> n4
n4 --> n5
@enduml
```

## Сравнение со штатным инструментом (cargo tree)

Штатный инструмент Cargo для просмотра зависимостей называется `cargo tree`.
Сравнение сделано для пакета `serde`.

Наша программа:
```
serde -> serde_core
serde_core -> (нет зависимостей)
```

`cargo tree` (проект, в который добавлен пакет serde командой `cargo add serde`,
версия serde 1.0.229):
```
rust-demo v0.1.0
└── serde v1.0.229
    └── serde_core v1.0.229
```

Для `serde` результаты совпадают: оба инструмента показывают одну зависимость
`serde_core`. В общем случае возможны такие расхождения:

1. **Версии.** `cargo tree` показывает версию каждого пакета и использует
   версии, выбранные в проекте. Наша программа берёт последнюю версию из
   реестра и выводит только имена.
2. **Возможности (features).** Мы пропускаем все необязательные зависимости.
   `cargo tree` включает те из них, которые подключены включёнными
   возможностями. Например, у `serde` необязательная зависимость
   `serde_derive` появляется только при включённой возможности `derive`.
3. **Платформа.** Мы пропускаем зависимости, привязанные к платформе.
   `cargo tree` показывает те, что подходят платформе, на которой запущен.
4. **Разделы зависимостей.** Мы читаем только обычные зависимости.
   `cargo tree` по умолчанию показывает ещё зависимости для сборки
   (build-dependencies), а для самого проекта — и для разработки
   (dev-dependencies).
5. **Корень дерева.** У `cargo tree` корень — проект пользователя (`rust-demo`),
   у нас корень — сам анализируемый пакет.
6. **Повторы.** `cargo tree` помечает уже показанные ветки знаком `(*)`, наша
   программа пишет `(уже показан)`. Смысл тот же.
7. **Обратные зависимости.** `cargo tree -i` ищет зависимые пакеты среди всех
   пакетов проекта. Наш режим `--reverse` работает только на тестовом
   репозитории, потому что для настоящего реестра у нас нет списка всех
   пакетов.
